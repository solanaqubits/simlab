# Claim Review Local API 0.1 — точный проект протокола

Статус: **SPECIFICATION / IMPLEMENTATION_PENDING**. HTTP-сервер не реализован.
База: UI-спецификация `e1aed33cf10f1e7263178f5901489e781ff3a430` и исполняемый
адаптер `e12325dbc10c39c7913cc66b2c01877a88f1856a`.

Артефакты: [запросы](request.schema.json), [ответы](response.schema.json),
[численные лимиты](limits.json), [проверка примеров](check_examples.py).
JSON Schema Draft 2020-12 описывает форму сообщений. Совпадение хешей, декодирование
байтов, управление процессами, авторизация и актуальность требуют отдельного кода
сервера; схемы не являются их реализацией или доказательством.

## 1. Транспорт, контекст и доступ

Один процесс сервера обслуживает один координаторский контекст в v0.1, слушает
только `127.0.0.1` на выделенном порту. Канонические Host и Origin задаются при
старте: **`127.0.0.1:<port>`** и **`http://127.0.0.1:<port>`**. `localhost` не
принимается автоматически как второй алиас. Это уточняет прежнее предложение
«127.0.0.1 или localhost»: в v0.1 выбран один точный origin. Forwarded/X-Forwarded-*
не меняют проверяемый адрес. `Origin: null`, отсутствие Origin и сторонний Origin
отвергаются для всех шести API-операций. Межсайтовый доступ не разрешается.

Координатор задаёт источник и ожидаемый хеш, ведомость и ожидаемый хеш,
claim-map-пакет и ожидаемый хеш его manifest.json, source claim ID, source revision
и новый каталог сессии. При старте сервер проверяет все закреплённые входы, включая
содержимое claim-map-пакета действующим проверяющим кодом. Неверная конфигурация
не создаёт рабочую сессию. `context_id` и UUID остальных объектов — непрозрачные
серверные UUIDv4 в нижнем регистре; ID не является средством авторизации.

Токен сессии: 32 случайных байта, представление base64url без padding. Передача
только в `Authorization: Bearer …`; никаких токенов в query, URL, журнале или
сохранённых карточках. Доставка токена координатором браузеру — вне этого data API,
по отдельному локальному каналу. Не добавляется незащищённый endpoint выдачи токена.
Токен не хранится в localStorage. Проверка Host/Origin и токена предшествует
чтению данных контекста; сервер не доверяет браузерному состоянию кнопок.

Все шесть операций — POST с `Content-Type: application/json` (допустим явный
`charset=utf-8`). Требуются один Content-Length, без Transfer-Encoding, сжатия
и неоднозначных повторов Host/Origin/Authorization/Content-Length/Content-Type.
Дубликаты этих заголовков отклоняются. Неизвестные методы/пути не запускают CLI.
Ответы с данными используют `Cache-Control: no-store`; CORS-доступ не открывается.
Запуск публичного или многопользовательского сервиса не входит в контракт.

## 2. Формат запросов и точные байты

Общие обязательные поля: `schema: claim-review-api-request-1`, `operation`,
`request_id`, `context_id`. Operation должен соответствовать пути, например
`artifacts/read` для `/v1/artifacts/read`. Неизвестные внешние поля запрещены;
клиент не передаёт файловые пути, argv, исполняемые файлы, токен в JSON или новые
baseline-хеши. Поля ожидаемого draft/artifact hash и context fingerprint —
предусловия сравнения, а не способ назначить серверу новую базу.

| POST-путь | Дополнительные обязательные поля | Успешный HTTP-ответ |
| --- | --- | --- |
| `/v1/context` | Нет | 200: закреплённый контекст, текущие состояния трёх якорей, ссылки на снимок/ведомость/manifest и limits |
| `/v1/drafts` | `parent_draft_id` (UUID или null), `record_sha256`, `record_base64` | 201: новый draft ID, хеш и размер, `validation_state: not_run` |
| `/v1/checks` | `draft_id`, `draft_sha256`, `context_fingerprint` | 202: ID задания и привязка к входной версии |
| `/v1/builds` | Те же поля | 202: ID задания и привязка к входной версии |
| `/v1/jobs/status` | `job_id` | 200: состояние задания, отчёты и зарегистрированные артефакты |
| `/v1/artifacts/read` | `artifact_id`, `artifact_sha256`, `offset`, `max_bytes` | 200: порция исходных байтов в Base64 и метаданные |

`record_base64` — стандартный RFC-style Base64 с алфавитом A–Z/a–z/0–9/+/, padding
`=`, без пробелов или переводов строк. Сервер обязан строго декодировать и
повторно закодировать значение: результат должен совпасть с входом. Regex схемы
сам по себе не проверяет каноничность неиспользуемых битов последней группы.
Decoded bytes — именно те UTF-8-байты, которые хешируются и сохраняются; никаких
переформатирований JSON или CRLF→LF. Неверный `record_sha256` отвергается.

Сохраняемый draft должен быть синтаксически корректным строгим UTF-8 JSON-объектом,
без BOM, одиночных суррогатов, дубликатов ключей, float/NaN/Infinity, с глубиной
не более 32 и целочисленными токенами не длиннее 128 цифр. Эти лексические проверки
выполняются до JSON Schema. В частности, JSON Schema `integer` не заменяет запрет
лексемы `1.0` нашим строгим парсером. Ошибки **Extraction-схемы внутри draft**
сохранять можно: это черновик с `not_run`, а не признанная валидная карточка.
Неизвестные поля внешнего API-запроса при этом по-прежнему запрещены.

`parent_draft_id` должен относиться к текущему контексту; null начинает независимую
ветку редактирования. Сервер не имеет скрытой «текущей версии», на которую можно
подменить явный draft ID. Родитель не перезаписывается. Никакого автоматического
закрытия вопросов или повышения свидетельств при сохранении нет.

## 3. Повторы запросов и актуальность

Для drafts/checks/builds ключ повтора — `(context_id, operation, request_id)`.
После успешного принятия повтор с теми же **сырыми байтами POST-тела** возвращает
тот же draft/job ID; повтор с другими байтами даёт 409 idempotency_conflict.
Проверка существующего ключа выполняется до проверки busy. Незавершённые или
отвергнутые запросы не считаются принятыми операциями. Читающие операции используют
request_id только для корреляции и не создают неограниченный кэш ответов.

Журнал принятых операций хранится в пределах сессии и заданных квот. После
перезапуска v0.1 создаётся новый контекст/токен; автоматическое восстановление
старой HTTP-сессии и exactly-once через перезапуск не заявляются. Архивы прежней
сессии остаются координатору, не перезаписываются и не выдаются как новая сессия.

`context_fingerprint` — SHA-256 детерминированного представления неизменяемых
якорей, claim ID, source revision и версии профиля лимитов. При реализации
необходимо использовать байтовое кодирование существующего `m.encoded` над
объектом с ключами `source_sha256`, `expectations_sha256`,
`claim_map_bundle_sha256`, `source_claim_id`, `source_revision`, `limits_profile`.
Токен, случайные ID и пути в fingerprint не включаются. Значение вычисляет сервер.

До приёма задания проверяются draft hash, fingerprint и все три внешних якоря.
Несовпадение даёт 409 без нового задания. Перед исполнением проверка повторяется:
входы читаются ограниченным безопасным способом, фиксируются в отдельном каталоге
задания и сверяются; CLI получает именно эти байты и закреплённые хеши. Проверка
одного manifest.json не заменяет проверку файлов исходного claim-map-пакета.
Изменение внешних файлов после формирования корректного снимка не меняет байты
принятого задания, но делает текущий контекст непригодным для новых запусков.

Ответ хранит исходные draft ID/hash и fingerprint. `historical`/`stale` — отношение
UI к своей редактируемой версии, не новый статус сервера или валидатора. Сервер
не знает о несохранённых правках браузера и не объявляет ответ актуальным для них.

## 4. Задания, исходы и ошибки процесса

На контекст разрешено **не более одного** принятого незавершённого задания.
Состояние queued занимает этот слот; отдельной очереди ожидания нет. Второй новый
запрос получает 409 context_busy. После 202 переход queued→running должен
произойти за 5 секунд, иначе failed/worker_failure.

Переходы: queued→running→completed|failed; возможен queued→failed при сбое подготовки.
На completed CLI вернул распознанный результат и правильный код выхода:

| Исполнитель | Результат | Код CLI |
| --- | --- | --- |
| Extraction | record_consistent | 0 |
| Extraction | needs_context / review_required | 1 |
| Extraction | invalid_input | 2 |
| Adapter | built | 0 |
| Adapter | build_blocked | 1 |
| Adapter | invalid_input | 2 |

HTTP job status в этих случаях — 200. Отказ адаптера — completed, а не авария.
В completed build обязательна квитанция Adapter; Extraction/Transport включаются
только если действительно запускались. Для built обязательны record_consistent
и contract_preserved. Повтор одного validator в reports запрещён. Для checks
передаётся ровно один Extraction-отчёт. Не выполненный этап не получает
выдуманного результата. Package_available true допустим только при built.

Таймаут, сбой подготовки снимка, превышение вывода/диска, авария процесса,
несоответствие кода выхода и JSON-отчёта, неверные привязки либо true в assurance
дают failed с failure.code. На failed отсутствуют принятые отчёты валидаторов;
доступны лишь отдельно проверенные диагностические артефакты. Отчёт со случайным
true нельзя молча исправить на false. Существующие исходы Extraction сохраняются
полностью; API их не переименовывает и не повышает статус свидетельства.

## 5. Численные пределы

Авторитетный машинный профиль — limits.json; context response содержит его
точную копию. Значения являются **проектными ограничениями**, а не измеренными
пределами производительности или гарантиями реального времени.

| Ресурс | Предел |
| --- | --- |
| POST-тело | 2 MiB = 2 097 152 байта, включая JSON/Base64 оболочку |
| Заголовки | 16 KiB суммарно, до 32 заголовков |
| Чтение POST-тела / отправка ответа | 5 / 10 секунд абсолютного времени соответствующей операции |
| Снимок / ведомость / decoded draft | По 1 MiB; ведомость+draft не более 2 MiB |
| Claim-map-пакет | 16 MiB по правилам существующего валидатора |
| Время CLI Extraction / Adapter | 60 / 180 секунд монотонных часов от старта процесса |
| Завершение после лимита | SIGTERM группе, до 2 секунд; затем SIGKILL и до 2 секунд ожидания |
| stdout / stderr | По 256 KiB байтов; чтение обоих потоков одновременно |
| Один выходной файл / все файлы задания | 16 / 64 MiB, включая снимки входов и журналы |
| Каталог сессии | 512 MiB; перед принятием задания резервируются 64 MiB |
| Количество draft / job | До 128 каждого, без автоматического удаления истории |
| API-нагрузка | 8 запросов/секунду, burst 16 на контекст |
| Чтение артефакта | Порция от 1 до 65 536 байтов |

Лимит CLI не включает дополнительные максимум 4 секунды попыток завершения.
Если процесс не завершился, слот не освобождается для нового задания: контекст
блокируется до операторского устранения. Чтение stdout/stderr ограничено по мере
поступления; нельзя сначала накопить неограниченный вывод в памяти. Запуск —
фиксированные аргументы без shell, отдельная группа процессов. Токен браузерной
сессии не передаётся в argv CLI и не попадает в журналы.

Учет диска включает неудачные/частичные задания. Резерв освобождается с учетом
фактически оставшихся байтов; переполнение не лечится незаметным удалением старых
квитанций. При нехватке квоты новые сохранения/запуски отклоняются, чтение уже
доступных данных остается разрешённым. Это требует серверной реализации контроля
записи; один лишь периодический подсчёт не заявляется жестким ограничением диска.

## 6. Артефакты и чтение порциями

Клиент передаёт только зарегистрированный UUID, ожидаемый хеш файла, offset в
**байтах** и max_bytes. Это не символьные диапазоны атомов! Ответ содержит хеш
целого файла, общий размер, offset, returned_bytes, eof и chunk_base64. EOF при
offset==size возвращает пустую порцию; offset>size даёт 416. Returned_bytes равно
длине декодированной порции; eof соответствует достижению конца файла.

При сборке UI декодирует Base64-порции в байты, собирает файл, проверяет полный
SHA-256, и только потом декодирует UTF-8. Граница порции может разрезать Unicode-
символ: нельзя декодировать каждую порцию как независимую UTF-8-строку.

Сервер проверяет принадлежность ID контексту, регистрацию и целостность файла.
Чтение ведётся из одной ограниченной проверенной байтовой версии (до 16 MiB),
не из повторно открываемого по клиентскому пути файла. Частичные каталоги и
незарегистрированные файлы не выдаются. Диагностические квитанции штатного отказа
разрешены после проверки; планы/кандидаты при отказе недоступны. На built регистрация
разрешена только после проверки манифеста, всех хешей и ложности четырёх флагов.
Все artifact refs и hash/size в них относятся к реальным проверенным файлам,
а не к заявленным клиентом метаданным.

## 7. HTTP-ошибки и обязательства вне схемы

| HTTP | error.code |
| --- | --- |
| 400 | malformed_request, invalid_schema, noncanonical_base64, invalid_record_json |
| 401 | unauthorized |
| 403 | origin_host_rejected |
| 404 | unknown_route, unknown_context, unknown_draft, unknown_job, unknown_artifact |
| 405 | method_not_allowed |
| 408 | request_timeout |
| 409 | draft_hash_mismatch, context_fingerprint_mismatch, anchor_mismatch, anchor_unavailable, context_busy, idempotency_conflict, artifact_unavailable, artifact_integrity_failure |
| 413 | payload_too_large |
| 415 | unsupported_media_type |
| 416 | range_not_satisfiable |
| 429 | rate_limited |
| 507 | quota_exceeded |
| 500 | internal_error |

При недоверенном/непрочитанном запросе operation/request_id/context_id в error
могут быть null. В ответах не раскрываются токены, пути или существование ресурсов
до авторизации. Retry_after_seconds используется только для временного ограничения
нагрузки; нормальный busy не обещает точного срока окончания. Сообщения — текст,
не исполняемая HTML-разметка. Неизвестная ошибка не маскируется под invalid_input CLI.

Сервер отдельно обязан проверить: соответствие operation пути, авторизацию,
строгий парсер, канонический Base64, длины decoded bytes, хеши, равенство expected
и observed для matched, владение ID, уникальность refs, точность offsets/eof,
контекст отчётов, idempotency, quotas и разрешённые переходы состояний. JSON Schema
не выполняет эти действия. Четыре assurance-флага в оболочке всегда false — это
граница гарантий API, не синтез отсутствующего результата проверки.

## 8. Проверка самой спецификации

`python3 -B geek_work/contracts/claim-review-api/check_examples.py` проверяет
метасхемы, 21 иллюстративное сообщение и 73 негативных изменения, а также согласие
лимитов. Использована уже установленная jsonschema 4.10.3; новая runtime-зависимость
CLI не добавляется. UUID/нулевые хеши в примерах — условные значения структуры,
не свидетельства существования файлов или выполненных заданий.

Первый прогон обнаружил принятие завершающего newline в Base64 из-за поведения
regex `$`. Все шаблоны ID/hash/Base64 исправлены на абсолютную проверку конца;
добавлены регрессии для hash и ID. История проверки сохранена отдельно.

Это **не HTTP-тесты**, не испытание CSRF/CORS, нагрузки, процессов, таймаутов или
файловой устойчивости. Сервер, UI и меры доступа ещё предстоит реализовать и
проверить на принятых сценариях. Ранее пройденные 134 теста CLI не объявляются
повторно запущенными в этом документационном проходе.

Добавлен [HTTP test harness](HARNESS.ru.md) для вызова будущего сервера и отдельные
самопроверки клиента. Это не реализация API-сервера; заглушка из self-tests не
подменяет его приёмку. Серверные таймауты, квоты и управляемые гонки остаются
следующим этапом.
