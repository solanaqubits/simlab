# Claim Review Local API: клиентский test harness

Реализован [geek_work_claim_api_harness.py](../../tools/geek_work_claim_api_harness.py)
поверх спецификации `2fadd78f53aca1170bc2ed418633635bab8e5b2b`.
Это клиент для будущего сервера, **не реализация HTTP-сервера или браузерного UI**.
Он отправляет настоящие HTTP-запросы только на явно заданный порт `127.0.0.1`.
Удалённый URL, DNS-имя, proxy, редиректы и произвольный путь не принимаются.

## Режимы и границы

| Режим | Проверяемые действия |
| --- | --- |
| `probe` | Контекст и профиль лимитов; отсутствие/неверный токен; неверные Host/Origin; дубликаты служебных заголовков; Transfer-Encoding, Content-Encoding; неизвестное внешнее поле пути; malformed JSON; чтение источника порциями и полный SHA-256 |
| `ready` | Всё из probe, затем сохранение готовой записи, повторы сохранения/заданий, конфликт идемпотентности, неверный draft hash, Extraction и Adapter до record_consistent/built/contract_preserved |
| `orbit` | То же, но ожидаются needs_context и build_blocked; package_available остаётся false |

Ready/orbit меняют состояние **отдельной тестовой сессии сервера**: создают draft
и два задания. Они не должны запускаться против рабочей редакторской сессии.
Probe не создаёт draft/job. Программа не меняет источники или ведомость координатора,
не запускает CLI самостоятельно и не создаёт случайные долгоживущие фоновые задачи.

Запросы идут с интервалом не менее 150 мс; polling — не чаще раза в 500 мс.
Это не нагрузочный тест. Второй самостоятельный запуск при занятом слоте здесь
не проверяется: быстрый реальный CLI может завершиться до следующего запроса,
поэтому нужен управляемый серверный fixture для воспроизводимого busy-сценария.
Повтор **того же** принятого запроса проверяется на прежний job ID независимо
от текущего состояния; это не новый запуск и не обязан получать context_busy.
Допускается не более одной активной задачи, включая queued; очереди ожидания нет.

Не покрыты и явно перечисляются в квитанции: изменение координаторского источника,
детерминированная занятость слота, CLI-таймаут и очистка процессов, квоты вывода/диска,
rate limiting, браузерная работа и поздний ответ после правки. Эти проверки требуют
следующего этапа реализации сервера и управляемых fault-injection фикстур.

## Проверка ответов

Клиент проверяет JSON Schema ответов, HTTP-код, Cache-Control: no-store, тип
содержимого, correlation IDs, соответствие error.code HTTP-коду и все четыре
assurance-флага. Для заданий контролирует draft ID/hash/fingerprint, отсутствие
перехода running→queued, итоговый результат и доступность пакета. Из артефактов
читает реальные квитанции: статус/имя схемы должны совпадать с summary, а имеющиеся
в успешных отчётах хеши должны соответствовать исходной версии и контексту.

Артефакты читаются по зарегистрированным ID, порциями до 64 KiB, с проверкой offsets,
EOF, канонического Base64, размера и SHA-256 целого файла. Граница между порциями
может проходить внутри UTF-8 emoji; сначала собираются байты, декодирование не
используется для вычисления byte offset. Проверки не доказывают, что сервер
действительно исполнил Lean или CLI: это контроль его наблюдаемого контракта.

В квитанцию попадают названия проверок, HTTP-коды и хеши ответов, но не тела ответов,
Authorization, токен или исходные тексты. Неизвестные исключения записываются по
классу, без потенциально чувствительного текста. Квитанция создаётся исключительно
в новом файле **до сетевых действий**; существующий файл блокирует запуск.
Успех относится только к выбранному профилю, не ко всей приёмке API.

## Как запускать после появления сервера

Необходим уже согласованный developer-инструмент `jsonschema` (в этом окружении
проверено на 4.10.3). Новых установок не выполнялось. Это зависимость harness,
а не изменение зависимостей существующих стандартно-библиотечных CLI.

Координатор запускает будущий сервер на отдельной тестовой конфигурации и передаёт
порт, context UUID и путь к локальному файлу токена. Сам токен не передаётся в argv.
В примере значения порта, UUID и пути необходимо заменить действительными:

```sh
python3 -B geek_work/tools/geek_work_claim_api_harness.py \
  --port 45678 \
  --context-id 00000000-0000-4000-8000-000000000002 \
  --token-file /path/to/private-session-token \
  --mode ready \
  --record geek_work/examples/claim-adapter-ready/record.json \
  --output /tmp/new-api-ready-harness-report.json
```

Для orbit нужен отдельный серверный контекст, закреплённый за историческими
входами орбиты, и `examples/claim-extraction-orbit/orbit-needs-context.json`.
Контекст готовой синтетической фикстуры не подменяется кандидатом орбиты.
Код завершения harness: 0 — выбранные проверки прошли, 1 — отказ/ошибка клиента
или проверок. Ошибки синтаксиса CLI и невозможность создать файл квитанции могут
завершить процесс раньше без готового отчёта. Четыре assurance-флага всегда false.

## Что проверено в этом локальном проходе

**28 самопроверок клиента прошли**:

- структурные/семантические проверки ответов и несовпадения их привязок;
- обработка ошибок, хешей, Base64, EOF и разрезанного UTF-8;
- идемпотентные маршруты ready/orbit на явно тестовой **модели в памяти**;
- собственная HTTP-передача клиента на минимальной контролируемой loopback-заглушке.

Заглушка не реализует серверный шлюз, авторизацию, квоты и CLI-исполнение.
Прохождение этих самопроверок **не является приёмкой Claim Review API**.
Реального продукта-сервера пока нет; режимы probe/ready/orbit против него
в этом проходе не запускались. 134 прежних CLI-теста повторно не запускались.

Самопроверки отделены от общего `geek_work/tests`, чтобы developer-зависимость
jsonschema не стала неявным требованием старого набора тестов:

```sh
python3 -B -m unittest discover \
  -s geek_work/contracts/claim-review-api/harness_tests -v
```

Тесты: [harness_tests/test_harness.py](harness_tests/test_harness.py).
Квитанция: harness-evidence/checks.json (`harness-evidence/checks.json`; historical reference, not included in this public package).
Публикация, новый Lean-аудит, граф знаний и удалённый CI не выполнялись.
